# 个人 Agent 工作台：产品与技术设计

- 日期：2026-10-25
- 状态：核心产品选择已与用户逐项确认；本文是首版实施基线
- 目标平台：Windows 本地桌面
- 首版深度适配：Claude Code、Codex
- 后续适配：Tencent WorkBuddy、Google Antigravity、ZCode

## 1. 产品定义

这是一个面向个人的本地 Agent 工作台。用户以项目为中心管理多个编码 Agent 的规则、skills、任务、对话交接与协作；整机首页负责跨项目发现和统计。工作台不替代各 Agent 的模型与执行器，只统一用户能够审阅和控制的部分。

核心价值是让用户从 Agent A 转到 Agent B 时，不必手工复制零散聊天内容，也能让两个 Agent 在同一项目中并行分工，最后审查并合并结果。

### 1.1 已确认的产品决定

1. 第一版优先解决项目内跨 Agent 共享和协作。
2. 交接由用户主动触发；默认不在后台同步记忆或对话。
3. 交接保留完整可见对话历史、任务进度、工具记录中可见且可取得的部分、文件变更和产物引用；隐藏推理不采集。用户还可以主动选择可读取的持久记忆并发布给其他 Agent。
4. 目标 Agent 新建任务接续工作，不伪装成源 Agent 的原生会话。
5. 第一版同时支持顺序交接与并行分工，并提供冲突协调和合并。
6. 并行编码任务默认使用独立 Git worktree；合并由用户审查确认。
7. 采用本地工作台加能力适配器；Claude Code 和 Codex 做深，其他三种逐步接入。
8. 首版为 Windows 本地桌面应用；项目共享配置可进 Git，完整交接历史默认只存在本机。
9. 用量统计保留原始口径和数据来源，缺失值显示未知。

### 1.2 不纳入首版

- 自动跨 Agent 后台同步对话或自动记忆。
- 隐藏思考过程、内部系统提示词或凭据的迁移。
- 把跨产品历史写入目标产品的私有会话数据库。
- 对所有外部启动的任务承诺暂停、终止或精确 token 统计。
- 云账号、多人协作、远程设备控制、统一模型计费。

## 2. 用户对象与主要流程

目标用户是同时使用两种以上 Agent 的个人开发者或知识工作者。首版围绕一个本地 Git 项目开展。

### 2.1 首次接入项目

用户选择项目目录。工作台检测 Git、Claude Code、Codex 和已有规则、skills，生成只读预览。用户选择哪些内容纳入共享层；发布到原生位置前查看差异并确认。项目目录中的共享内容可被 Git 跟踪；会话和用量数据库留在本机应用数据目录。

### 2.2 顺序交接

用户在任务页选择源会话和目标 Agent。工作台读取完整可见记录，列出无法获取的内容、过大附件、敏感字段提醒和工作区状态。用户预览、可手工删改交接副本，然后确认。工作台保存不可变的源记录快照和交接版本，在目标 Agent 新建任务，发送任务入口与交接包路径。目标 Agent 可按时间、角色和关键字读取完整原始记录。源会话保持原样。

完整存档与一次性模型上下文是不同概念：存档不能因目标模型窗口不足而截断；首轮输入提供任务目标、目录索引、最近进展和读取方法，完整历史仍可由目标 Agent 逐段读取。界面必须显示已传入首轮的内容与仅存档可读取的内容。

### 2.3 并行分工

用户建立一个 workflow，加入顺序步骤和并行分支，指定 Agent、输入、完成条件和审查点。每个会写代码的并行分支有独立 worktree 与任务记录。完成后工作台展示分支差异、测试结果和冲突；用户选择合并顺序，必要时在隔离区解决冲突，确认后才写入目标分支。未完成或失败的分支可保留、重试或丢弃；不自动删除有改动的 worktree。

### 2.4 整机首页

整机首页汇总已登记项目、可发现的 Agent、用户级规则与 skills、工作台管理的运行任务以及用量。对于外部应用启动的任务，只展示适配器能可靠获取的信息和可执行操作。项目页显示项目级配置、任务、workflow、交接时间线、合并队列与统计。

## 3. 核心概念与边界

- Project：一个规范化的本地目录及其 Git 仓库身份；目录移动后可重新绑定。
- AgentInstallation：工具、版本、可执行位置、可用接口及登录健康状态；不保存登录凭据。
- Adapter：某 Agent 的能力探测、配置读写、会话读取、任务启动与控制、事件及用量解析实现。
- SharedArtifact：用户维护的项目知识、规则、skill 或 workflow；有版本、范围、目标 Agent 和发布记录。
- MemoryEntry：从用户选定的原生记忆或手工材料导入的持久知识条目；记录来源、原文、范围、时间和发布状态，不与会话历史混为一类。
- NativeArtifact：Agent 原有文件；只有用户选择后才导入共享层。
- Task：用户目标及状态，归属项目；可包含多个 Run。
- Run：某 Agent 在某个工作区的一次执行，记录来源、会话 ID、状态和事件。
- HandoffPackage：不可变源快照加可审阅的交接副本；记录来源和目标，支持完整性校验。
- Workflow：由步骤与依赖构成的有向无环图；步骤可顺序或并行。
- UsageRecord：带来源、口径、时间和可信等级的用量事实；未知不等于零。
- MergeProposal：一个或多个 Run 的差异、验证证据、冲突和用户决定。

所有单元通过明确接口通信。项目模型不依赖某个 Agent 的专有文件格式；适配器不直接改任务调度状态；界面不直接读写第三方配置。

## 4. 系统结构

    React UI
       │ Electron IPC：带类型的命令与事件
       ▼
    本地应用核心
       ├─ Project Registry / SQLite 元数据
       ├─ Shared Artifact Publisher / 差异与回滚
       ├─ Handoff Service / 完整存档与检索
       ├─ Workflow Scheduler / 状态机
       ├─ Workspace Manager / Git worktree 与合并
       ├─ Usage Aggregator / 来源标记
       └─ Adapter Registry
          ├─ Claude Code Adapter
          ├─ Codex Adapter
          └─ 后续适配器

采用 Electron、React、TypeScript 和 SQLite。主进程独占文件系统、进程和 Git 操作；渲染进程仅通过受限 IPC 访问。关闭 Node integration、开启 context isolation、校验 IPC 参数和项目路径。应用不启动公网服务；如后期需要本机 API，再单独设计认证与权限。

### 4.1 存储分层

项目仓库中的 .agent-workbench/ 仅保存可审阅、可版本化的项目共享配置：project.json、knowledge.md、rules/、skills/ 和 workflows/。创建前给用户预览文件清单。原生规则和 skill 文件由发布器按目标 Agent 格式生成或引用；每次发布保存前后哈希和备份，以便回滚。

Windows 的 %LOCALAPPDATA%/AgentWorkbench 保存 SQLite、完整会话快照、交接包、事件日志、用量记录和运行缓存；使用本地数据目录，避免长历史进入漫游配置。数据库仅保存文件索引及哈希，大文本和附件以内容寻址文件保存，避免数据库膨胀。敏感内容默认不写入 Git。用户可导出一个交接包，但导出前必须预览。

### 4.2 适配器能力协商

每个适配器实现探测与只读清单，并声明细粒度能力。能力集合至少包括：发现安装、发现项目会话、读取完整可见历史、读取用户可见持久记忆、读取配置、发布配置、将用户选定记忆发布成目标工具可用的项目指导、启动任务、流式状态、继续任务、暂停／终止、精确用量、skill 调用证据。能力可因版本、登录模式或项目而变化。按钮由实时能力决定，不能仅凭 Agent 名称决定。

能力状态有 supported、unsupported、unknown、degraded；每项附证据来源、最近探测时间及失败原因。探测失败不删除既有数据，也不把能力误判为支持。

### 4.3 首版适配策略

Claude Code：优先使用官方 Agent SDK 的会话读取能力和可用的执行接口。官方材料说明 SDK 可列出并读取本地会话消息，且与 Claude Code CLI 的本地记录相通；具体 Windows 版本、认证方式、事件字段和取消行为必须在适配器原型中验证。[Claude Agent SDK 会话浏览示例](https://platform.claude.com/cookbook/claude-agent-sdk-05-building-a-session-browser)

Codex：优先使用官方 app-server 协议读取、启动、流式跟踪与中断任务。官方文档描述 thread/read、thread/turns/list、turn/start 和 turn/interrupt；具体用户现有 Codex 桌面会话的可见范围必须在原型中验证。Codex 本地自动记忆属于生成状态，允许用户查看和选取，但不直接改写其生成文件；稳定项目要求发布到 AGENTS.md。[Codex App Server](https://learn.chatgpt.com/docs/app-server)、[Codex 记忆](https://learn.chatgpt.com/docs/customization/memories)

后续三种：Tencent WorkBuddy 的记忆导入目前有用户粘贴摘要的官方流程，不能据此承诺原生对话双向导入。[WorkBuddy 记忆文档](https://www.workbuddy.ai/docs/zh/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/Memory) Antigravity CLI 提供会话范围、结构化输出与记录路径，可用于后续原型验证。[Antigravity 对话管理](https://antigravity.google/docs/cli/conversations/)、[Antigravity Headless](https://antigravity.google/docs/cli/headless/) ZCode 官方迁移工具目前说明可导入 Claude Code 历史，且其项目记忆和 AGENTS.md 是不同层次；其他方向仍需验证。[ZCode 安装与迁移](https://zcode.z.ai/en/docs/install)、[ZCode Agent 说明](https://zcode.z.ai/en/docs/agents)

### 4.4 本地逻辑数据模型

SQLite 中的主表为 projects、agent_installations、native_sessions、tasks、runs、run_events、handoffs、memory_entries、shared_artifacts、publications、workflows、workflow_nodes、merge_proposals 和 usage_records。各表使用内部 UUID 主键；第三方 ID 只作为带 Agent 命名空间的外部引用，不能单独作全局主键。Project 对 Task、Workflow、SharedArtifact 是一对多；Task 对 Run 是一对多；Handoff 引用一个源 Session 和一个目标 Run；Run 可引用一个受管理的 worktree。

原始消息和附件不塞入关系表，由内容哈希指向 %LOCALAPPDATA%/AgentWorkbench/blobs。数据库存元信息、索引、角色、时间、字节数、来源和完整性状态；全文索引只覆盖用户允许索引的可见文字。删除项目登记时先展示其本机历史、worktree 与共享文件清单，分别由用户选择删除；默认保留原生 Agent 数据和项目仓库文件。应用不自动清理完整交接存档，仅在空间不足时提示用户选择归档或删除。

## 5. 完整交接包

交接包使用版本化 manifest.json 与独立内容文件。至少保存：

- 源项目、Agent、会话 ID、导出时间、源版本、内容哈希；
- 所有可取得的用户和助手可见消息，原始顺序、角色、时间戳、附件引用；
- 可取得的工具调用和结果、命令退出码、文件修改摘要；
- 任务目标、当前状态、待办、已做决定、失败与阻塞；
- Git 基线、当前提交、未提交差异的引用；
- 完整性报告：读取条数、缺失／截断项目、附件大小、来源可靠性；
- 用户在交接副本中的删改及其审计记录。

系统不主动读取隐藏推理、凭据文件、环境变量或第三方私有数据库。可见历史本身可能含有用户或工具输出的敏感内容；扫描器提示疑似密钥、个人信息和大文件，由用户在交接副本中删改，源快照不变。若源工具只提供部分历史，界面显示“不完整”，用户可附加手工导出的文件；绝不称作完整交接。

为避免上下文窗口溢出，接收端先拿到任务入口和历史索引，并能按区间、角色、关键词检索原文。系统不以自动摘要替代原文；可选摘要仅作为导航。启动前显示预计首轮 token 范围及“原文在存档中”的提示。

### 5.1 用户触发的持久记忆互转

持久记忆与对话交接是两个独立操作。用户可从适配器能读取的用户可见记忆中选择条目，也可粘贴或导入自己导出的记忆文件。工作台保留原文与来源，提供范围选择（整机偏好或项目知识）、重复项检测、冲突预览和编辑，然后发布为目标 Agent 能可靠读取的项目指导文件或任务上下文。只有目标工具提供明确的原生记忆写入接口时，才显示“写入原生记忆”；否则标为“发布为项目指导”或“随任务提供”，不声称改写了目标工具的自动记忆。

首版对 Claude Code 和 Codex 验证可读取的记忆来源及原生规则路径。Claude Code 将 CLAUDE.md 与自动记忆区分，Codex 也把本地生成记忆与必须遵守的 AGENTS.md 分开；因此跨工具发布要保留来源标签，不能把自动生成的事实无审查地升级成强制规则。[Claude 记忆概念](https://platform.claude.com/cookbook/tool-use-context-engineering-context-engineering-tools)、[Codex 记忆与规则](https://learn.chatgpt.com/docs/customization/memories)

## 6. 规则、skills 与 workflow

项目共享内容是用户选择的规范来源，不强行覆盖 Agent 自带能力。发布器维护“共享版本—上次发布版本—当前原生版本”三方关系。若原生文件自上次发布后变化，显示差异和三个选择：保留原生、用共享覆盖、人工合并。每次写入采用临时文件加原子替换，备份原文件；失败时恢复。

Skill 清单分为已发现、已启用、可用于某项目、实际调用四个维度。只有运行事件或明确日志证据才能增加“实际调用”计数；仅在目录里发现 SKILL.md 不能算调用。跨 Agent 共享 skill 时复制/映射其文件与资源，记录兼容性告警；执行脚本的权限由目标 Agent 自己管理。

Workflow 首版使用 DAG 数据模型，但 UI 仅提供顺序步骤与并行分支编辑器。节点有 agent、输入、工作区策略、完成条件、依赖和审查门；支持暂停调度、重试失败节点、跳过可选节点。运行中的 Agent 是否能被暂停取决于适配器能力。节点输出包含产物引用与验收证据。需要写同一仓库的并行节点强制隔离；非 Git 项目首版只允许顺序任务和只读并行任务。

项目默认同时运行最多两个写入节点，用户可在 workflow 中降低并发数；提高并发上限需要查看预估工作区占用。任务完成条件至少可选“Agent 报告完成”“指定命令退出码为 0”“用户审查通过”，其中前两项的证据都展示在节点详情。Agent 报告完成不自动通过合并审查。

## 7. 任务与合并状态

Task：draft → ready → running → review_required → completed；任意运行状态可进入 failed 或 cancelled。Run：queued → starting → running → waiting_for_user → succeeded / failed / cancelled。状态转换由核心状态机执行，事件幂等写入，应用重启后从持久化状态和外部进程探测恢复。

并行工作区以项目 Git 基线提交创建。合并提案记录每个分支的基线、已提交与未提交变更、未跟踪文件、测试命令及结果。工作台在临时集成 worktree 中按用户选择的顺序试应用这些变更，展示差异与冲突；用户确认后才将结果应用到目标工作区。合并前再次检查目标分支 HEAD 与提案基线；若发生变化，重新计算，不执行过期合并。冲突只在临时集成 worktree 中解决，原分支保持可恢复。工作台不会自动提交或推送，除非用户在具体操作中明确选择。

## 8. 统计口径与界面

统计事实有 sourceType（managed_event、documented_local_record、manual_import）、quality（exact、verified_import、unknown）、agent、project、task、run、model、时间、input／output／cache／reasoning token、原始字段和去重键。汇总按源事实求和；同一会话从两处读取时按会话 ID、事件 ID 和时间去重。不同 Agent 的总 token 可作为活动量展示，不能默认等同于费用或相同工作量。缺失字段保持 null。费用只在提供方给出可靠价格或账单且用户明确启用时另行展示。

首版页面：
1. 整机首页：Agent 安装状态、运行任务、项目入口、总用量与数据覆盖率。
2. 项目概览：Agent 能力表、最近任务、待审查交接与合并。
3. 配置与记忆页：共享知识、用户选定的原生记忆、规则、skills、原生差异与发布历史。
4. 任务页：任务看板、Run 时间线、状态与可用控制。
5. 交接向导：选源、完整性检查、预览／删改、选目标、启动结果。
6. Workflow 页：顺序／并行编辑、节点状态和审查门。
7. 合并页：分支差异、验证结果、冲突处理与确认。
8. 用量页：项目／Agent／模型筛选、原始口径、来源与未知覆盖率。

## 9. 隐私、故障与可恢复性

应用默认仅本地运行，不采集遥测、不读取 Agent 登录令牌、不要求用户交出 API key。进程以当前用户权限运行；文件系统访问限制在用户选定项目和必要的 Agent 配置目录。所有跨 Agent 写入、终止任务、合并和导出都由用户明确触发。交接内容可能包含敏感数据，预览和检测是强制步骤；检测不能代替用户判断。

SQLite 开启 WAL，迁移有版本和备份。启动时检查上次未完成写入和孤儿 worktree。文件发布与合并有事务日志；崩溃后提供恢复界面。适配器异常隔离，不使整个应用退出。工具升级导致字段变化时降级到只读能力，标注原因。日志默认不记录完整 prompt 或凭据，诊断包导出前预览。

## 10. 验收标准

首版可发布的条件：

1. 在 Windows 上从空白环境登记一个 Git 项目，发现 Claude Code 与 Codex，并正确报告缺失或未登录状态。
2. 从各自可读取的完整可见会话生成交接包；条数、顺序、哈希与源记录一致；不可取得的内容明确标注。
3. 用户确认后能在另一个 Agent 新建任务，并从目标任务检索交接包中的任意原始消息；源会话不被更改。
4. 两个 Agent 能在独立 worktree 中并行运行，合并页能识别同文件冲突；用户拒绝合并时主分支不变。
5. 共享规则和 skill 发布前能查看差异，外部改动能被检测，失败可回滚。
6. 工作台管理的任务可显示实时状态、可用控制和精确事件用量；无数据的字段显示未知。
7. 应用异常退出后重启，任务、交接包、待合并分支可恢复。
8. 交接与导出前显示敏感信息预览；原始存档、删改副本及操作记录可区分。
9. 用户可选取一条可读取的原生持久记忆，审查后发布到另一个 Agent 可读的项目指导或任务上下文；界面准确区分这些目标位置与原生自动记忆。

## 11. 开发阶段与风险门

阶段 A：验证 Claude Code／Codex 的读取、启动、事件、取消和用量接口，确认 Windows 登录方式。若某能力不可用，适配器显式降级并调整对应 UI，不绕过官方认证读取私有令牌。

阶段 B：交付项目模型、配置发布、完整交接、两个深度适配器与单任务运行。

阶段 C：交付 workflow、并行 worktree、差异审查和合并。

阶段 D：交付整机首页、统计、安装包和恢复能力。

阶段 E：按能力逐个接入 Antigravity、ZCode、Tencent WorkBuddy。每个适配器单独通过兼容性测试；不因某一工具限制降低核心模型的数据完整性标准。

主要风险是第三方接口变化、既有会话权限差异、长历史占用空间、token 口径不一致、跨分支文件冲突和敏感内容外泄。对应措施是能力探测与降级、源快照完整性报告、内容寻址与保留策略、原始口径保留、隔离合并、交接前预览。

## 12. 开放的实现验证项

这些不是产品决定，必须在阶段 A 用实测关闭：

- Claude Code Agent SDK 在目标 Windows 安装与用户现有订阅登录下的运行方式、读取范围和事件字段。
- Codex app-server 对用户既有桌面任务的读取范围、线程权限、用量事件和取消语义。
- 两个 Agent 对交接包本地文件的读取行为与最大输入限制。
- worktree 中各 Agent 对项目级规则和 skills 的发现路径。
- 并行运行时文件锁、进程回收与 Windows 路径长度处理。

验证失败时以能力矩阵降级，不篡改第三方私有存储，不把估算数据称为精确数据。
